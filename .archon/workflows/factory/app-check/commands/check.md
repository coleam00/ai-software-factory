Changed files: `$INPUTS.files`. Depth: `$INPUTS.depth`. App config: `$INPUTS.config`. Expected holdout IDs: `$INPUTS.expected_holdouts`.

1. Before changing directories, resolve `.archon/workflows/factory/app-check/scripts/app-process.ts` from this workflow's original working directory to an absolute path. Use that absolute helper path for every `app-process.ts` command below. Never load the helper from the prepared PR checkout, which may contain an older package. Every shell invocation of the helper must explicitly set the `ARTIFACTS_DIR` environment variable to this run's exact path: `$ARTIFACTS_DIR`. For PowerShell, put `$env:ARTIFACTS_DIR = '$ARTIFACTS_DIR'` before invoking the helper in that same command. Agent tool shells do not automatically inherit this workflow variable. Then `cd` to the prepared checkout. Read MISSION.md and the issue criteria. If the app config's `runtime` is empty, load `agent-browser skills get core --full` before browser work and follow steps 2 and 3. If `runtime` is set, follow **Runtime mode** below instead of steps 2 and 3, and never load agent-browser.
2. Before starting an app, run `bun .archon/workflows/factory/app-check/scripts/app-process.ts support`. If it does not report `supported: true`, do not start the app; record the limitation as `INCOMPLETE`. If `app.prepare` is non-empty, run exactly that documented preparation command in the checkout. Choose a free localhost port. Start `app.start` directly with `app.port_env` set to that port and retain the native launcher process object/handle (on Windows, use `Start-Process -PassThru`, not a detached PID-only shell launch). If `app.database_env` is non-empty, set it to a fresh temporary database path. From that retained object read `Id` and `StartTime.ToFileTimeUtc()`, then immediately run `bun .archon/workflows/factory/app-check/scripts/app-process.ts record <PID> <CREATION_FILETIME>`; the helper compares the launcher identity with a newly opened handle before writing the versioned record under `$ARTIFACTS_DIR/app-check/`. Never write a bare PID. If the configured command cannot be started directly with a retained handle, or identity recording fails, mark the check `INCOMPLETE` and stop only through the exact launcher handle you retained; never fall back to a numeric PID. After recording succeeds, wait for `app.health_path`. Never invent a setup command, kill by name, or close browser sessions you did not open.
3. At light depth, start/smoke and check each criterion. At normal depth, also exercise each criterion through the UI and the core journeys MISSION.md names. At deep depth, cover boundary/error states too.

**Runtime mode** (app config `runtime` is set). The file at `runtime` is the owner's instructions for running this app: how to set it up, start it, drive it, stop it, and what must hold. Read all of it first; it outranks generic habits.

- R1. From the checkout, run its setup and then its start exactly as written (never invent a setup command). Use the port its start reports everywhere the instructions say `<PORT>`. Stop the app only with its teardown, run from the checkout, before you finish; the cleanup node runs `app.teardown` again if you exit early. Never kill by name, and never stop an instance another checkout started.
- R2. Drive the app only through what the instructions provide (its maintained driver, its input endpoints, its normal-mode driver). Do not write your own bot when a driver command exists; batch driver commands into one script call. Back every behaviour criterion with something you observed through the running app's own input path. Do not use a tool, recording or check that this pull request adds or changes as your only evidence for a behaviour.
- R3. Depth decides scope. light: setup, start once, confirm health and identity, check each criterion; no probes. normal: also observe each criterion through the real input path and try up to three things a player would plausibly do with the new behaviour (one `P<n>` line each). deep: also check user-visible criteria in normal mode when the instructions provide it, and run every instructions assertion the change could affect. Do not go deeper for reassurance, and stay inside what this change touches: regressions elsewhere are the default branch's checks' job.
- R4. Report each criterion as a `C<n>` line, each probe as a `P<n>` line. A probe that surprises a player is a FAIL that names what it saw. An assertion of the instructions that you ran is an `A<n>` line naming the assertion id. A capability the merged build does not expose yet is not a failure of this change: leave it out unless the issue's criteria need it.
- R5. A timing or frame-rate measurement taken while the machine is loaded is INCOMPLETE, not FAIL: say so, and rerun it once. A check that can run longer than about 9 minutes must be started detached the way the instructions describe and waited for in bounded foreground waits. Keep the whole check under 30 minutes; the scope is this change, not the product.

4. At normal or deep depth, only now read scenario files in the configured holdout directory and run every ID in `$INPUTS.expected_holdouts`; run none at light. The manifest step read filenames only, so this is the only node that may read scenario contents. Report only each `H-<id>`, verdict, and visible result. Never quote scenario contents in the report, output, prompt, or public comment.
5. Save screenshots, logs, and observations under `$ARTIFACTS_DIR/app-check/`. Open every screenshot you cite. Close only browser sessions you opened. Stop the app only with `bun .archon/workflows/factory/app-check/scripts/app-process.ts stop`; it verifies the recorded identity before termination and retires the record only after the owned process has exited. Do not use `kill`, `taskkill`, `Stop-Process`, or any other PID-based fallback. The workflow cleanup node calls the same helper if this checker exits early.

Write `report.md` and `result.json` there. `result.json` is `{ "overall": "PASS|FAIL", "lines": [string...], "summary": string }`. Every line must be exactly:

`C<n>  PASS|FAIL|INCOMPLETE  <one sentence>  evidence: <file>`

or `H-<id>`, `P<n>` or `A<n>` in place of `C<n>`. Use one evidence file per line, relative to the app-check artifact folder or absolute. INCOMPLETE means the check could not finish and counts as failure. Overall is PASS only if every line passes. Include at least one `C<n>` line and exactly one line for every expected holdout ID (and no other holdout ID). Put the identical lines in report.md. Return the same object.
